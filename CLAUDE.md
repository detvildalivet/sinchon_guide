# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sinchon Guide (frontend app name: **Sinchon Guide**, package `com.sinchonguide`) — a place-recommendation app for the Sinchon area. One linear pipeline: **ask what the user needs → categorize the answer → recommend a real nearby place → guide them there.** Two independent apps in one repo:

- `backend/` — FastAPI + SQLAlchemy + SQLite (`sinchon_guide.db`)
- `frontend/` — React Native 0.85 (TypeScript), no web build

User-facing strings are Korean, in the formal 하십시오체 register (e.g. "~하십시오", "~습니다") rather than casual 해요체 — keep new UI copy consistent with this. The app does not own a place catalog: Kakao Local API supplies candidates live, and Google Places API (New) enriches the nearest few with rating/open-now data. Neither is cached server-side — the server persists only `User`, `Visit` (per-user visit history), and `HistoryClear` (see Architecture below).

**Current development focus: Android only.** iOS is deferred — see *iOS status (deferred)* under Architecture before doing any iOS work.

## Commands

### Backend (run from `backend/`)

```sh
pip install -r requirements.txt
uvicorn app:app --reload --env-file .env   # serves http://localhost:8000, docs at /docs
pytest                                     # unit tests — no network, no DB, except test_visits.py (below)
```

Test files: `test_recommendation.py` (scorer), `test_places.py` (need-type filter + category/address extraction), `test_enrichment.py` (Google match/parse logic incl. `rating_count`), `test_routes.py` (TMAP GeoJSON→RouteOut transform), `test_classify.py` (free-text→category classification incl. the curated/open/fail-soft paths), `test_password.py` (password policy + that `register()` checks it before touching `db`), `test_auth.py` (JWT round-trip + `require_jwt_secret`), `test_api_errors.py` (`request_external_api`'s provider-error-shape parsing). `test_visits.py` is the one exception that touches a DB: it spins up a self-contained in-memory SQLite session to exercise `list_visits`/`clear_visits`' real query logic (ordering, per-user filtering, and — critically — that clearing never touches the separate personalization-count query in `routers/recommendations.py`).

Modules use flat top-level imports (`from database import ...`), so the working directory must be `backend/` — there is no package, no `alembic`, no migration path. Tables are created by `Base.metadata.create_all` at import time in `app.py`, with default `checkfirst=True` — this creates any table that doesn't exist yet but never `ALTER`s an existing one, so adding a *column* to an existing table (`User`/`Visit`/`HistoryClear`) still requires deleting/recreating `sinchon_guide.db`.

Requires four provider env vars to actually serve `/recommendations`, `/routes`, and `/classify`: `KAKAO_REST_API_KEY` (Kakao Developers REST API key — not the JavaScript or Native App key — for place search), `GOOGLE_PLACES_API_KEY` (Places API (New) key, for the rating/open-now enrichment pass — see `services/enrichment.py`), `TMAP_APP_KEY` (SK Open API key, Pedestrian product, for walking routes), and `GEMINI_API_KEY` (Google AI Studio key, for the free-text need-classification pass — see `services/classify.py`; free to obtain and use at this volume via Google AI Studio's free tier, which is why classification runs on Gemini rather than Claude). Easiest way to provide them locally: create `backend/.env` (gitignored) with all four vars set and pass `--env-file .env` to `uvicorn`. All four are read lazily at call time (not import time) via `services/api_errors.require_kakao_key()`/`require_google_key()`/`require_tmap_key()`/`require_gemini_key()`, so the app still boots and `pytest` still runs without them — missing/invalid keys surface as a clear JSON error (500 if unset, 502 with the provider's own message if it rejects the request) instead of an opaque crash. These keys are server-side only and must never be shipped to the client. **The Google key must NOT be IP-restricted** while the backend runs on a dev machine's dynamic IP — an IP-restricted key is exactly what broke this app's Google integration once already on an IP change (see `require_google_key()`'s hint text in `services/api_errors.py`, referred to internally as the `googleghost` failure mode); use no application restriction (or an API restriction to Places API (New) only) plus a billing budget cap instead, and only switch to IP restriction once the backend is deployed behind a stable egress IP. (`GOOGLE_PLACES_API_KEY` and `GEMINI_API_KEY` are both Google Cloud/AI Studio credentials but for entirely unrelated products — Places API (New) vs. the Gemini API — don't conflate them.)

A fifth env var, `SINCHON_JWT_SECRET`, is required for auth to be meaningful at all — it's the HMAC key `auth.py` signs every access token with, read lazily via `services/api_errors.require_jwt_secret()` the same way as the four provider keys above (fail-fast 500 if unset, app still boots and `pytest` still runs without it). Unlike the provider keys, **there is no hardcoded fallback** — a fallback string committed to a public repo is equivalent to no signature at all, letting anyone forge a token for any `user_id`. Set it to a long random value (e.g. `python -c "import secrets; print(secrets.token_urlsafe(48))"`) in `backend/.env`; rotating it invalidates every previously issued token, which is expected.

## Architecture

### Backend

- `app.py` mounts five routers: `users`, `recommendations`, `routes`, `visits`, `classify`.
- Auth: JWT via python-jose (`auth.py`), bcrypt password hashing, 1-week tokens, login endpoint `users/login`. Secret comes from `SINCHON_JWT_SECRET` env var, read lazily via `services/api_errors.require_jwt_secret()` — no fallback; fails fast with a clean 500 if unset (see the env-var section above for why).
- `services/password.py` — the account signup password policy (8–20 chars, at least 2 of letter/digit/symbol — "letter" is any Unicode letter, so Korean passphrases pass; whitespace counts toward no class). `schemas.py`'s `UserCreate` deliberately has no pydantic-level length constraint (that would surface as a "Value error, ..." 422 leaking into the Korean UI) — `routers/users.py`'s `register()` calls `validate_password()` explicitly first, before touching `db`, for a clean 400 instead. `frontend/src/utils/password.ts` mirrors this rule by hand for the live signup checklist — there is no shared source of truth between the two languages; parity is enforced only by matching test case tables in `tests/test_password.py` and `__tests__/password.test.ts`. Change one, change both.
- `services/places.py` — the only source of place breadth. `search_nearby(lat, lng, need_type)` dispatches on whether `need_type` is one of 4 curated categories or an open one. For the curated 4 (`meal`/`cafe`/`drinks`/`dessert`), it calls **Kakao Local API** around the user's location (~1.2km radius): the category-search endpoint for `meal`/`cafe` (clean `category_group_code` buckets, FD6/CE7), the keyword-search endpoint for `drinks`/`dessert` (Kakao has no dedicated category code for bars or dessert shops — they're subcategories of FD6/CE7, so a keyword like "술집"/"디저트" narrows within the group), then post-filters results by `_matches_need_type` against Kakao's `category_name` breadcrumb string (tested in `tests/test_places.py`) — a broad category bucket can include things that don't belong, e.g. a cafe surfacing under a `meal` search. For anything else — an open Korean place-type keyword `services/classify.py` extracted from free text, e.g. "당구장" — `_search_keyword` runs a plain Kakao keyword search instead, with no `category_group_code` and no post-filter, trusting Kakao's own relevance ranking. Both paths build the same candidate dict shape and share `_short_category`. Kakao's `category_name` and `road_address_name`/`address_name` are kept (via `_short_category`) and surfaced to the client as `category`/`address` on `RecommendationOut`. Nothing is persisted — candidates are plain dicts passed straight to enrichment and scoring. Kakao candidates come back sorted nearest-first (`sort=distance`).
- `services/enrichment.py` — fills in the `rating`/`open_now`/`rating_count` fields Kakao can't supply, by calling **Google Places API (New)**'s Text Search endpoint once per candidate (no batch endpoint exists), concurrently via a thread pool, for only the nearest `DEFAULT_TOP_N=8` candidates (`routers/recommendations.py` calls `enrich_candidates(candidates)` right after `search_nearby`, mutating the candidate dicts in place). A Kakao candidate is matched to a Google Text Search result only if it's within `MATCH_RADIUS_METERS` (80m) **and** the names overlap (`_is_plausible_match`) — either check failing is treated as no match, not a fuzzy accept, since a false match would show a real-looking but wrong rating for a different place. Enrichment is fail-soft per candidate: a network error, empty result, or implausible match just leaves that candidate's fields `None` (their pre-enrichment default) — the whole `/recommendations` call never fails because one Google lookup failed. Only a missing/misconfigured `GOOGLE_PLACES_API_KEY` aborts the call, via `require_google_key()`. The field mask requested (`rating`, `userRatingCount`, `currentOpeningHours.openNow`, `regularOpeningHours.openNow`) deliberately excludes `reviews`/`editorialSummary`, which would bump the request from Google's Enterprise SKU to the pricier Enterprise+Atmosphere SKU. Budget/price-level data was tried here twice and abandoned both times (Kakao has none; Google's price-level field came back null for nearly every real Sinchon candidate) — there is no budget concept anywhere in this pipeline now; don't re-add it without re-verifying that premise. Tested in `tests/test_enrichment.py` (pure matching/parsing logic + `enrich_candidates` with the network call monkeypatched).
- `services/classify.py` — the "ask what the user needs" → "categorize the answer" step (`routers/classify.py`'s `POST /classify`), and the only thing standing between `AskScreen`'s free-text box and a real Kakao search. `classify_need_type(text)` sends the free-text Korean sentence to **Gemini's Flash-Lite tier** (`gemini-flash-lite-latest` — the `-latest` alias, not a dated snapshot like `gemini-2.5-flash-lite`, which 404s for newer accounts even though it's still listed by `models.list()`) via Google AI Studio (`google-genai` SDK). A single `classify_need` function declaration is passed with `tool_config`'s `FunctionCallingConfig` forced to `mode="ANY"` + `allowed_function_names=["classify_need"]`, so the response always contains exactly one forced function call, read via `response.function_calls`, with `args["type"]` in `["meal", "cafe", "drinks", "dessert", "other"]` plus an optional `args["keyword"]` string. One of the 4 curated values is returned as-is (drives `services/places.py`'s category-code path); `"other"` with a non-empty `keyword` returns that keyword stripped (routed to the open `_search_keyword` path instead); `"other"` with an empty/missing `keyword` returns `None` — the sole "couldn't tell what the user wants" signal. Deliberately fail-soft on everything except a missing/misconfigured key: a `None`-mapping classification, a malformed response, or any Gemini API failure all return `None` rather than raising, so `/classify` never 500s. Only `require_gemini_key()` aborts (a config error, not a per-request miss). The Gemini API key lives only here; it is never shipped to the client. Tested in `tests/test_classify.py` with the `genai.Client` monkeypatched.
- `services/api_errors.py` — shared helper for all four external call sites (`services/places.py` → Kakao, `services/enrichment.py` → Google, `routers/routes.py` → TMAP, `services/classify.py` → Gemini): `require_kakao_key()`/`require_google_key()`/`require_tmap_key()`/`require_gemini_key()`/`require_jwt_secret()` raise a clean JSON 500 if the respective env var is unset, `request_external_api()` turns any upstream rejection into a JSON 502 carrying the provider's own error message (parsing both Google/TMAP's `{"error": {"message": ...}}` shape and Kakao's top-level `{"message": ...}` shape, falling back to raw response text otherwise — tested in `tests/test_api_errors.py`). Without this, misconfiguration (bad key, wrong IP restriction, wrong TMAP product subscribed) is indistinguishable from any other crash.
- `services/recommendation.py` — pure scorer, no DB/network. `score_candidates(candidates, user_lat, user_lng, visit_counts_by_place=None)` computes, per candidate: `distance_minutes` from haversine distance; a rating bonus (the candidate's `rating`, or a neutral `3.5` default when unrated, so an unenriched candidate isn't penalized); a personalization bonus from `visit_counts_by_place` (capped at 4 past visits × weight 0.5); and a hard `-1000` penalty when `open_now is False` (never fires on `None`, so an unenriched or "hours unknown" candidate isn't punished). **Ranking policy is closest-first with a closed-place override**: `score = -(distance_minutes * 10) + rating_bonus + personalization - closed_penalty`, so an open place always outranks a closed one regardless of distance, but among open (or unknown-hours) places, distance dominates and rating/visit-history only break near-ties. `reason` stays a bare `도보 N분` string — rating/open-now/category/address are surfaced as their own `RecommendationOut` fields (rendered via `RatingStars`/`OpenStatusBadge`/`PlaceMeta` on the frontend) rather than folded into this prose. Tested in `tests/test_recommendation.py`.
- `routers/recommendations.py` — `POST /recommendations` ties the above together: Kakao Local candidates (`search_nearby`) → `enrich_candidates` fills in rating/open-now/rating_count for the nearest few via Google → the user's per-place visit counts (grouped from `Visit`) → `score_candidates` → ranked list.
- `routers/routes.py` — `POST /routes` proxies **TMAP's Pedestrian Route API** (walking mode) for the walking-path coordinates + distance, called only for the place the user actually picked (not for every candidate). The pure transform from TMAP's GeoJSON response to `RouteOut` lives in `tmap_geojson_to_route()`, tested in `tests/test_routes.py`. `services/api_errors.request_external_api()` only guards the HTTP call itself (connection error + non-2xx status) — a 2xx response whose body isn't valid JSON, or is valid JSON but not the expected `{"features": [...]}` dict shape, is guarded separately: `compute_route()` catches a `response.json()` parse failure, and `tmap_geojson_to_route()` itself rejects a non-dict payload — both as a clean `502` instead of an unhandled exception. This was hit for real with a degenerate origin/destination pair (emulator GPS defaulting to California, destination in Seoul) that TMAP couldn't route.
- `routers/classify.py` — `POST /classify` (auth-gated, no DB dependency) turns `ClassifyIn.text` into `ClassifyOut.type` via `services/classify.classify_need_type()`. `type` is `null` on the wire when classification wasn't confident — not an error response.
- `routers/visits.py` — `POST /visits` records that the user was guided to a place; written best-effort (fire-and-forget, `.catch(() => {})`) from `App.tsx`'s `openGuide`, as soon as the user commits to being guided (tapping "이 장소로 안내") — not gated on `GuideScreen`'s Naver Map handoff button, since a user who never leaves the in-app map should still show up in history. `GET /visits` lists the user's own history, newest-first, capped at `HISTORY_LIMIT=50`, for `HistoryScreen`. `DELETE /visits` (`clear_visits`) lets the user clear what they see — it does **not** delete or modify any `Visit` row; it upserts a `HistoryClear(user_id, cleared_at)` marker (a dedicated table, not a column on `User`/`Visit`, precisely so `create_all`'s no-`ALTER` behavior didn't force a `sinchon_guide.db` reset — see `models.py`), and `list_visits` filters out rows at/before that cutoff. Deliberately, the personalization query in `routers/recommendations.py` (`visit_counts_by_place`) never consults `HistoryClear` — it reads `Visit` directly, so a cleared visit keeps counting toward recommendations forever; clearing is a visible-history concept only. Repeat clears just push the cutoff forward, so a visit made after a clear naturally reappears until the next one.

### Frontend

- **No navigation library.** `App.tsx` holds a manual `route` state (`'ask' | 'guide' | 'history'`), but **`AskScreen` is always mounted** — `GuideScreen` and `HistoryScreen` are layered on top of it via `CrossfadeSwitch` (`visible={route === 'guide'}` / `'history'`), not swapped in via a route-keyed conditional render. This is deliberate: swapping `AskScreen` out on every trip to `GuideScreen` would reset it to its initial `'type'` step on return, so pressing "다시 추천받기" would look like it dumped the user back to the home screen instead of the result they'd picked from. `backToAsk()` only flips `route` — it deliberately does **not** clear `picked`/`need`, leaving `GuideScreen` mounted-but-hidden so its own state (fetched route, map) survives the round trip; `HistoryScreen` follows the same pattern via a one-way `hasOpenedHistory` flag (set on first open, never cleared). `goHome()` (wired to `GuideScreen`'s 홈 button) is the one deliberate exception: it bumps an `askResetToken` counter that `AskScreen`'s effect watches to call `startOver()`, resetting it back to the `'type'` step — the only path that does reset `AskScreen` while still leaving `GuideScreen` mounted-but-hidden the same way `backToAsk` does. Auth gating happens in `Root` via `src/auth/AuthContext.tsx` (token persisted with AsyncStorage in `src/api/authStore.ts`); no token → `AuthScreen` directly.
- `AuthScreen` — 로그인 needs only 이메일/비밀번호; 회원가입 additionally asks 이름/생년월일/닉네임, plus a live password checklist driven by `src/utils/password.ts`'s `checkPassword()` (see `services/password.py` above). The 생년월일 field auto-formats digits into `YYYY-MM-DD` as the user types (`formatBirthDate` strips non-digits and re-inserts the hyphens); `DATE_RE` validation expects exactly that shape.
- `AskScreen` — a 2-step flow: `type → result`. **No category button grid** — the `type` step is a pure LLM inquiry slot: a free-text field ("어떤 곳을 찾으십니까?", placeholder "예: 당구장, 헬스장, 조용한 카페 등") plus a "찾기" button that submits the text itself, not a category. Submitting calls `POST /classify`; a non-null `ClassifyResult.type` — one of the 4 curated values, or an arbitrary Korean keyword like "당구장" the classifier extracted — hands into `chooseType()`, calling `/recommendations` immediately and caching the full ranked candidate list. When classification returns `null`, or the `/classify` call itself fails, `typeError` renders a short inline retry message under the input — the text field stays populated and editable. The result step shows the top-ranked candidate as a hero — name, `RatingStars` (or "평점 없음"), an `OpenStatusBadge`, and a `PlaceMeta` line (walk time + category) — plus every other candidate below it as a scrollable "다른 후보" list. Tapping a candidate row (`selectCandidate`) **promotes it to the hero card and scrolls to top — it does not navigate to `GuideScreen`**; only the hero card's "이 장소로 안내" button does that (`guideTo`). A header ☰ button (`onOpenHistory`) opens `HistoryScreen`. There is no budget field anywhere in this pipeline (`Need = {type, lat, lng}`, `src/types/recommendation.ts`) — tried twice on the backend, abandoned both times; see `services/enrichment.py` above.
- `GuideScreen` — fetches the walking route for the picked place, renders `LiveMapView` with the pick marker, the route as a `NaverMapPathOverlay` (coordinates come straight from `POST /routes`, no decoding needed), and the live user-location dot. Floating buttons: 다시 추천받기 (`onBack` → `backToAsk`) and 홈 (`onGoHome` → `goHome`, see above). The bottom card shows `RatingStars` (or "평점 없음"), an `OpenStatusBadge`, and a `PlaceMeta` line (walk time, category, address), plus a "네이버 지도로 안내" button that opens Naver Map's walking-directions deep link (`nmap://route/walk?...`, falling back to the Play Store listing if not installed) — it does not write the `Visit` itself; see `routers/visits.py` above for why that happens earlier, in `App.tsx`'s `openGuide`.
- `HistoryScreen` — opened from `AskScreen`'s header ☰ button. Shows the logged-in user's nickname/email plus a **로그아웃** button (`AuthContext.logout`), and the visit history from `GET /visits`. Takes a `visible` prop and refetches every time it transitions into view rather than only on first mount, since `App.tsx` keeps it mounted-but-hidden like `GuideScreen`. A "기록 지우기" action (behind an `Alert.alert` confirmation whose copy states exactly what happens) calls `DELETE /visits`; see `routers/visits.py` above for why this never touches the recommendation scorer's personalization signal.
- `src/hooks/useUserLocation.ts` + `src/services/locationService.ts` — the location source for both screens' `Need.lat/lng` and map regions. Falls back to a fixed Sinchon-station coordinate when permission is denied/unavailable (never some other neighborhood, since that would silently mis-locate every downstream Places search); `regionCovering()` computes the smallest region framing two coordinates (user + destination) without needing a `MapView` ref. Also runs a continuous `watchPosition` once the initial fix is granted, since (unlike `react-native-maps`) Naver's location overlay has no GPS tracking of its own. **`USE_MOCK_LOCATION` (`locationService.ts`, on by default under `__DEV__`) overrides both `requestCurrentLocation()` and `watchPosition()` to a fixed Yonsei-main-gate coordinate.** This exists because the Android emulator's default GPS fix is Google HQ in Mountain View, California — a *granted* permission, so the denied/unavailable fallback above never kicks in. Flip the flag off to test against a real/emulator-set GPS fix.
- `src/design/` — the shared style/token layer (`theme.ts` colors/spacing/radius/typography/shadow; `shellStyles.ts` panel/prompt-card shells, incl. the `chip`/`chipText` pill reused by `OpenStatusBadge`; `layout.ts` screen scaffolding). `src/components/` holds the presentational primitives built on it (`AppButton`, `IconButton`, `TouchableFade`, `Icon`, `EmptyState`, `Skeleton`, `MapMarkerPin`, `CrossfadeSwitch`, `RatingStars`, `OpenStatusBadge`, `PlaceMeta`, `LiveMapView`) — screens compose these rather than styling inline. `RatingStars` renders an explicit "평점 없음" (never blank) when `rating` is null — Google only enriches the nearest few candidates, so a missing rating is common and expected — plus a `(N)` rating-count suffix when Google supplied it. `OpenStatusBadge` renders 영업 중/영업 종료/영업정보 없음 from `openNow`; `null` renders as "영업정보 없음" rather than nothing, since hiding it entirely is exactly how a user could get routed to a closed place with no warning. `PlaceMeta` renders the walk-time + category line (plus address, only on `GuideScreen`'s card).
- `src/constants/needTypes.ts` — `NEED_TYPE_LABELS` maps the 4 curated identifiers to their Korean label (식사/카페/술 한잔/디저트); `needTypeLabel(type)` looks up that table and falls back to the raw string for anything else, since an open category (e.g. "당구장") already arrives as a human-readable Korean keyword needing no translation. `HistoryScreen`'s history rows go through `needTypeLabel()` rather than indexing `NEED_TYPE_LABELS` directly, since a visit's `type` can now be an open category that isn't in the table.
- `src/api/config.ts` picks the API host per platform: Android emulator → `10.0.2.2:8000`, iOS simulator → `localhost:8000`. Physical devices need the machine's LAN IP edited in that file.
- **Current focus: Android only. iOS is deferred** (see *iOS status* below). Android is developed and tested on an Android Studio emulator with a Google Play Services system image (native build via `npm run android`) — this is the only supported dev/demo target right now.

### Providers — who owns what stage

Four independent providers, one stage each, no overlap:

- **Kakao Local API** (backend, `KAKAO_REST_API_KEY`) — finds *what's nearby*. Given the user's location + need type, returns real businesses (name, coordinates, category) within ~1.2km. Called from `services/places.py`. This is the only place-search breadth in the app — Naver's Maps product family (NCP) has no place/POI search API at all (five products: Dynamic Map, Static Map, Directions 5/15, Geocoding, Reverse Geocoding), and Naver's separate Local Search API (`openapi.naver.com`) is keyword-only, capped at 5 results, with no coordinate/radius parameter — a poor fit for "closest-first, radius-bounded" search. Google Places was the original search source and was removed from that role (see *Routing in South Korea* below for the related, still-current Google-routing restriction) — it is not coming back to search.
- **Google Places API (New)** (backend, `GOOGLE_PLACES_API_KEY`) — fills in *what Kakao can't say*: rating, open-now, and rating count, for the nearest few candidates only. Called from `services/enrichment.py`, after Kakao search and before scoring — enrichment of Kakao's results, not a replacement for Kakao search. Must have **Places API (New)** enabled, and must **not** be IP-restricted while the backend runs on a dynamic dev-machine IP (see the env-var section above for why).
- **TMAP Pedestrian Route API** (backend, `TMAP_APP_KEY`) — computes *how to walk there*. Given a start/end coordinate pair (only for the place the user actually picked), returns the walking path geometry + distance/time. Called from `routers/routes.py`. The app registered for this key must have the **보행자 경로안내 (Pedestrian)** product subscribed — a **TMAP 대중교통 (Transit)**-only key will not authorize this endpoint.
- **Naver Maps SDK** (frontend, `naver_map_client_id`) — *draws it all on screen*: the map tiles, the live user-location dot, the destination pin, and the TMAP-supplied route line. Purely client-side rendering — it doesn't search for places or compute routes itself. `frontend/.env` (gitignored) holds `naver_map_client_id` — a Naver Cloud Platform (NCP) Maps client ID. **One client ID covers both platforms** (the NCP application is registered with both an Android package name and an iOS bundle ID). `android/app/build.gradle` reads it and injects it into `AndroidManifest.xml` via a `manifestPlaceholder` (`com.naver.maps.map.NCP_KEY_ID`); iOS wiring (Info.plist) is added when iOS work resumes. Requires the Naver Maven repo (`https://repository.map.naver.com/archive/maven`) added to `android/build.gradle`. A missing/blank `naver_map_client_id` fails the Gradle build at configure time with a `GradleException` naming the missing var, rather than silently building an app that installs fine but shows blank map tiles at runtime — this key isn't a true secret (it's embedded in every install and restricted by package name on the NCP console, not by being hidden), so failing loud on it is purely about catching a missing `.env` early, not about protecting the value.
- `src/components/LiveMapView.tsx` wraps `@mj-studio/react-native-naver-map` (`NaverMapView`) — Android only for now (see *iOS status*). `MapMarkerPin` wraps `NaverMapMarkerOverlay`; `GuideScreen`'s route line is a `NaverMapPathOverlay`. **`MapMarkerPin` requires explicit `width`/`height` props** (matching its child `View`'s own size, e.g. `GuideScreen`'s `PIN_SIZE` constant) — a custom-`View` marker has no intrinsic size for the native side to measure, and `NaverMapMarkerOverlay` silently renders nothing at all for it without an explicit size. This bit us once already (destination pin missing while the route line rendered fine) — if a pin silently stops appearing after touching `MapMarkerPin`, check this first.
- `Linking.canOpenURL('nmap://...')` (used by `GuideScreen`'s handoff button) requires a `<queries>` entry for the `nmap` scheme in `AndroidManifest.xml` — Android 11+ package-visibility rules make it silently return `false` otherwise, even with Naver Map installed.
- No OpenStreetMap/tile-overlay dependency.

### Routing in South Korea: Google Routes doesn't work, TMAP does

Google Routes' `computeRoutes` reliably 404s ("No walking route found") for every real Sinchon origin/destination pair — confirmed by calling it directly (HTTP 200, empty `{}` body, no `routes` key) versus the identical request shape with non-Korea coordinates (returns a normal route). This isn't a key, field-mask, or request-format problem: South Korea's Act on National Spatial Data Infrastructure restricts export of detailed (1:5,000-scale) map data to servers outside the country, and Google's routing servers are outside Korea. Google can still return place *search* results (Places API is unaffected) but not turn-by-turn route geometry. Conditional export approval was granted in Feb 2026, but as of this writing it has not produced working API routing.

**Fix applied:** `routers/routes.py` calls **TMAP's Pedestrian Route API** (`apis.openapi.sk.com/tmap/routes/pedestrian`) instead — TMAP is a Korea-based provider and isn't subject to the export restriction. The response (GeoJSON `LineString`/`Point` features) is transformed by the pure `tmap_geojson_to_route()` into `RouteOut.coordinates`, a plain `{latitude, longitude}` list that feeds `NaverMapPathOverlay` directly (no polyline encode/decode round trip). `GuideScreen`'s external handoff button opens Naver Map's walking-directions deep link, not Google Maps.

### iOS status (deferred)

Out of scope right now — captured here so the constraints aren't rediscovered later. **No Expo tooling is installed** (this is bare React Native CLI). The Windows dev machine has **no iOS Simulator** (requires macOS/Xcode), so iOS needs a physical device or a Mac. Two possible paths, each with trade-offs:

- **Stock Expo Go on a physical iPhone** — a fixed prebuilt binary that runs the JS bundle but **cannot load custom native pods**. Only modules Expo Go already ships work: `react-native-safe-area-context` ✅, `@react-native-async-storage/async-storage` ✅ — but **`@react-native-community/geolocation` ✗** (Expo ships `expo-location` instead) and **`@mj-studio/react-native-naver-map` ✗** (not an Expo Go built-in; it does ship an Expo config-plugin for prebuild, but that only helps the *next* path, not stock Expo Go). So on this path the map wouldn't render at all — this path is effectively closed now that the renderer is Naver, not `react-native-maps`.
- **Custom dev client via EAS Build** — cloud macOS build, no local Mac required; supports all native modules (geolocation, Naver Map's iOS SDK via its Expo config-plugin or manual Podfile wiring) but needs EAS setup and a physical device. This is now the only realistic iOS path.

The backend's web-service APIs (Kakao Local, TMAP Routes) are plain HTTPS `fetch` calls from the **backend**, not native modules on the client — so they work regardless of which iOS path is chosen, once iOS is picked back up.

### Android native build (Windows)

- New Architecture is on (`newArchEnabled=true` in `android/gradle.properties`), so every native module gets a Fabric codegen C++ target compiled via CMake/Ninja. **Do not set this to `false`** — RN 0.85's app-level build runs the Fabric/CMake configure step unconditionally regardless of this flag, but a third-party library's own `build.gradle` (e.g. `@mj-studio/react-native-naver-map`'s) typically gates *its own* codegen generation behind this same property. Flip it to `false` and the app still tries to `add_subdirectory` into that library's (now never-generated) `.../android/build/generated/source/codegen/jni/`, which fails CMake configure with "which is not an existing directory" — this is exactly what happened on this branch once (turning it off as a workaround attempt and never turning it back on) and cost real time to root-cause. If you hit that CMake error after adding a native dependency, check this flag first. CMake also mirrors each source file's full absolute path under the build directory, which on Windows can blow past the 260-character `MAX_PATH` limit — this repo's own path is long enough to trigger it (hit first on `react-native-safe-area-context`).
- `android/app/build.gradle` sets `externalNativeBuild.cmake.buildStagingDirectory` to a short temp-dir path to shave the build-dir prefix, but that alone isn't sufficient — the mirrored `node_modules` source path is the bigger contributor. The real fix is enabling Windows long-path support (`LongPathsEnabled=1` registry key + `git config --system core.longpaths true`, needs a reboot) or moving the project to a short path. If a `Filename longer than 260 characters` Ninja error resurfaces after adding a new native dependency, this is why.
- Gradle's autolinking (`settings.gradle`'s `autolinkLibrariesFromCommand()`) caches its `react-native config` output in `android/build/generated/autolinking/` and `android/app/build/generated/autolinking/`, gated by a hash of `package.json`/`package-lock.json` — it only re-runs when that hash changes. If a native package is added to `package.json` *before* it's actually present in `node_modules` (e.g. committed mid-install, or `npm install` interrupted), the hash is already "current" by the time `node_modules` catches up, so a later `npm install` alone won't invalidate the cache — the module silently never gets linked (missing from the generated `PackageList.java`, no Fabric view manager compiled), even though `npx react-native config` correctly reports it and the app builds/installs without error. Symptom: a JS-level "Cannot read property '<Component>' of undefined" for a native view, only when that screen actually mounts — a plain Metro cache reset + `npm run android` rebuild does *not* fix this, since the stale autolinking cache is untouched by either. Fix: delete `android/build/generated/autolinking/` and `android/app/build/generated/autolinking/` (or `./gradlew clean`) to force regeneration, then rebuild. Hit with `@mj-studio/react-native-naver-map` on this branch after it was reinstalled following an earlier missing-`node_modules` incident.
