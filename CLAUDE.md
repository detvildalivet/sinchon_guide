# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sinchon Guide (frontend app name: **Sinchon Guide**, package `com.sinchonguide`) — a place-recommendation app for the Sinchon area. One linear pipeline: **ask what the user needs → categorize the answer → recommend a real nearby place → guide them there.** Two independent apps in one repo:

- `backend/` — FastAPI + SQLAlchemy + SQLite (`sinchon_guide.db`)
- `frontend/` — React Native 0.85 (TypeScript), no web build

User-facing strings are Korean, in the formal 하십시오체 register (e.g. "~하십시오", "~습니다") rather than casual 해요체 — keep new UI copy consistent with this. The app does not own a place catalog — Kakao Local API supplies candidates live; the server only keeps a thin per-place annotation cache and per-user visit history (see Architecture below). (Google Places was the original *search* source and was fully removed from that role — see *Place search: Kakao Local API* below. Google later returned in a narrower, enrichment-only role — see `services/enrichment.py` — to supply rating/open-now data Kakao doesn't have. Price-level was fetched there too at first, but was dropped — see the `AskScreen` bullet below.)

**Current development focus: Android only.** iOS is deferred — see *iOS status (deferred)* under Architecture before doing any iOS work.

## Commands

### Backend (run from `backend/`)

```sh
pip install -r requirements.txt
uvicorn app:app --reload --env-file .env   # serves http://localhost:8000, docs at /docs
pytest                                     # unit tests (tests/test_recommendation.py — scorer; tests/test_places.py — need-type filter + category/address extraction; tests/test_enrichment.py — Google match/parse logic incl. rating_count; tests/test_routes.py — TMAP GeoJSON→RouteOut transform) — no network, no DB. tests/test_visits.py is the one exception: it spins up a self-contained in-memory SQLite session to exercise list_visits/clear_visits' real query logic (ordering, per-user filtering, and — critically — that clearing never touches the separate personalization-count query in routers/recommendations.py)
```

Modules use flat top-level imports (`from database import ...`), so the working directory must be `backend/` — there is no package, no `alembic`, no migration path. Tables are created by `Base.metadata.create_all` at import time in `app.py`, with default `checkfirst=True` — this creates any table that doesn't exist yet (a brand-new model like `HistoryClear` needs no manual DB action on next start) but never `ALTER`s an existing one, so adding a *column* to an existing table (`User`/`Visit`/`PlaceAnnotation`) still requires deleting/recreating `sinchon_guide.db`.

Requires three provider env vars to actually serve `/recommendations` and `/routes`: `KAKAO_REST_API_KEY` (Kakao Developers REST API key — not the JavaScript or Native App key — for place search), `GOOGLE_PLACES_API_KEY` (Places API (New) key, for the rating/open-now enrichment pass — see `services/enrichment.py`), and `TMAP_APP_KEY` (SK Open API key, Pedestrian product, for walking routes). Easiest way to provide them locally: create `backend/.env` (gitignored) with all three vars set and pass `--env-file .env` to `uvicorn` (uvicorn's built-in dotenv loading, no app code involved). All three are read lazily at call time (not import time) via `services/api_errors.require_kakao_key()`/`require_google_key()`/`require_tmap_key()`, so the app still boots and `pytest` still runs without them — missing/invalid keys surface as a clear JSON error (500 if unset, 502 with the provider's own message if it rejects the request) instead of an opaque crash. These keys are server-side only and must never be shipped to the client. **The Google key must NOT be IP-restricted** while the backend runs on a dev machine's dynamic IP — an IP-restricted Google key is exactly what broke the app's original (now-removed) Google Places integration on IP changes (`googleghost.png`); use no application restriction (or an API restriction to Places API (New) only) plus a billing budget cap instead, and only switch to IP restriction once the backend is deployed behind a stable egress IP.

A fourth env var, `SINCHON_JWT_SECRET`, is required for auth to be meaningful at all — it's the HMAC key `auth.py` signs every access token with, read lazily via `services/api_errors.require_jwt_secret()` the same way as the three provider keys above (fail-fast 500 if unset, app still boots and `pytest` still runs without it). Unlike the provider keys, **there is no hardcoded fallback** — an earlier version of this file (`dev-secret-change-me`) let anyone forge a token for any `user_id`, since the string was public in this repo and nothing loaded `.env` outside of `uvicorn --env-file .env`. Set it to a long random value (e.g. `python -c "import secrets; print(secrets.token_urlsafe(48))"`) in `backend/.env`; rotating it invalidates every previously issued token, which is expected.

## Architecture

### Backend

- `app.py` mounts four routers: `users`, `recommendations`, `routes`, `visits`.
- Auth: JWT via python-jose (`auth.py`), bcrypt password hashing, 1-week tokens, login endpoint `users/login`. Secret comes from `SINCHON_JWT_SECRET` env var (falls back to a dev default).
- `services/places.py` — the only source of place breadth. Calls **Kakao Local API** around the user's location (~1.2km radius): the category-search endpoint for `meal`/`cafe` (clean `category_group_code` buckets, FD6/CE7), the keyword-search endpoint for `drinks`/`dessert` (Kakao has no dedicated category code for bars or dessert shops — they're subcategories of FD6/CE7, so a keyword like "술집"/"디저트" narrows within the group). Budget is **not sent to Kakao at all** — Kakao has no price-level concept, request-side or otherwise (see *Place search: Kakao Local API* below for why). Results are post-filtered by `_matches_need_type` against Kakao's `category_name` breadcrumb string (tested in `tests/test_places.py`) — same defensive purpose as the old Google-era check (a broad category bucket can include things that don't belong, e.g. a cafe surfacing under a `meal` search). Kakao's `category_name` and `road_address_name`/`address_name` are also kept (via `_short_category`, tested in `tests/test_places.py`) and surfaced to the client as `category`/`address` on `RecommendationOut` — previously read only for filtering, then discarded. Upserts a `PlaceAnnotation` row per surviving result (thin cache keyed by Kakao's `place_id` — never a full catalog mirror). Kakao candidates come back sorted nearest-first (`sort=distance`).
- `services/enrichment.py` — fills in the `rating`/`open_now` fields Kakao can't supply, by calling **Google Places API (New)**'s Text Search endpoint once per candidate (no batch endpoint exists), concurrently via a thread pool, for only the nearest `DEFAULT_TOP_N=8` candidates (`routers/recommendations.py` calls `enrich_candidates(db, candidates)` right after `search_nearby`). Google is used here strictly as an *enrichment* source — not for search breadth, routing, or map tiles, which stay on Kakao/TMAP/Naver respectively (see *Maps and place search* below for why Google was removed from those roles and stays removed from them). A Kakao candidate is matched to a Google Text Search result only if it's within `MATCH_RADIUS_METERS` (80m) **and** the names overlap (`_is_plausible_match`) — either check failing is treated as no match, not a fuzzy accept, since a false match would show a real-looking but wrong rating for a different place. Enrichment is fail-soft per candidate: a network error, empty result, or implausible match just leaves that candidate's two fields `None` (its pre-enrichment default) — the whole `/recommendations` call never fails because one Google lookup failed. Only a missing/misconfigured `GOOGLE_PLACES_API_KEY` aborts the call, via `require_google_key()`. The field mask requested (`rating`, `currentOpeningHours.openNow`, `regularOpeningHours.openNow`) deliberately excludes `reviews`/`editorialSummary`, which would bump the request from Google's Enterprise SKU to the pricier Enterprise+Atmosphere SKU. `priceLevel` was in this mask too originally (feeding a budget-fit tiebreaker and a budget question in `AskScreen`) but was dropped: live testing across all three budgets at the same Sinchon coordinates showed only 1 of 12 candidates ever got a non-null `price_level` from Google, and the tiebreaker's weight was too small next to distance/rating to matter even when present — so `가성비`/`적당히`/`플렉스` essentially never changed the recommendation. Removing `priceLevel` doesn't change the billing tier (confirmed against Google's docs — `rating`/opening-hours alone already trigger the Enterprise SKU). `userRatingCount` was already in the field mask (no extra billing-tier cost) but used to be parsed away; it's now kept as `rating_count` (`ratingCount` on the wire) so the frontend can show "4.3 (128)" instead of a bare number. Enriched `rating` (not `open_now` — time-sensitive, never cached) is persisted back onto the candidate's existing `PlaceAnnotation` row; that row's `price_level` column is no longer written and stays `None`. Tested in `tests/test_enrichment.py` (pure matching/parsing logic + `enrich_candidates` with the network call monkeypatched).
- `services/api_errors.py` — shared helper for all three external call sites (`services/places.py` → Kakao, `services/enrichment.py` → Google, `routers/routes.py` → TMAP): `require_kakao_key()`/`require_google_key()`/`require_tmap_key()` raise a clean JSON 500 if the respective env var is unset, `request_external_api()` turns any upstream rejection into a JSON 502 carrying the provider's own error message. Without this, misconfiguration (bad key, wrong IP restriction, wrong TMAP product subscribed) is indistinguishable from any other crash — just "HTTP 500" with no detail. (Was `google_errors.py`/`require_api_key()`/`request_google_api()` in the old full-Google era — renamed when Google Places search was removed; `require_google_key()` was added back once Google returned in the narrower enrichment-only role.)
- `services/recommendation.py` — pure scorer, no DB/network. Ranking policy: **closest-first** (walking distance dominates); rating and open-now are near-tie breakers, plus per-place visit-history personalization. These are live (not dormant) for the top `services/enrichment.py` candidates that got a Google match — `rating`/`open_now` are real values there, and the scorer's existing `Optional`-safe handling (`open_now is False` never fires on `None`) means un-enriched tail candidates (beyond the enrichment cutoff, or with no plausible Google match) still degrade cleanly to closest-first + per-place visit-history, exactly as every candidate did before enrichment existed. `budget`/`price_level` were removed as scoring inputs entirely (see `services/enrichment.py` above and the `AskScreen` bullet below) — `score_candidates()` no longer takes a `budget` parameter. `reason` stays a bare `도보 N분` string — rating/open-now/category/address are surfaced as their own `RecommendationOut` fields (rendered via `RatingStars`/`OpenStatusBadge`/`PlaceMeta` on the frontend) rather than folded into this prose, so a missing value doesn't just silently vanish from the text. Tested in `tests/test_recommendation.py`.
- `routers/recommendations.py` — `POST /recommendations` ties the above together: Kakao Local candidates → `enrich_candidates` fills in rating/open-now for the nearest few via Google → the user's per-place visit counts → scorer → ranked list. `need.budget` is still accepted on the wire (see `AskScreen` bullet) but isn't passed to the scorer.
- `routers/routes.py` — `POST /routes` proxies **TMAP's Pedestrian Route API** (walking mode) for the walking-path coordinates + distance, called only for the place the user actually picked (not for every candidate). Google Routes was tried first but is legally blocked for Korean coordinates (see *Routing in South Korea* below); TMAP is a Korea-based provider and isn't subject to that restriction. The pure transform from TMAP's GeoJSON response to `RouteOut` lives in `tmap_geojson_to_route()`, tested in `tests/test_routes.py`. `services/api_errors.request_external_api()` only guards the HTTP call itself (connection error + non-2xx status) — a 2xx response whose body isn't valid JSON, or is valid JSON but not the expected `{"features": [...]}` dict shape, is guarded separately: `compute_route()` catches a `response.json()` parse failure, and `tmap_geojson_to_route()` itself rejects a non-dict payload — both as a clean `502` instead of an unhandled exception surfacing to the client as a bare, undetailed `HTTP 500`. This was hit for real with a degenerate origin/destination pair (emulator GPS defaulting to California, destination in Seoul) that TMAP couldn't route.
- `routers/visits.py` — `POST /visits` records that the user was guided to a place; written best-effort (fire-and-forget, `.catch(() => {})`) from `App.tsx`'s `openGuide`, as soon as the user commits to being guided (tapping "이 장소로 안내" or a candidate row in `AskScreen`) — not gated on `GuideScreen`'s Naver Map handoff button, since a user who never leaves the in-app map should still show up in history. (This moved here after visits were briefly recorded only from the Naver handoff instead: an un-awaited `postVisit` there raced `Linking.openURL` backgrounding the app to launch Naver Map, silently dropping the write.) `GET /visits` lists the user's own history, newest-first, capped at `HISTORY_LIMIT=50`, for `HistoryScreen`. `DELETE /visits` (`clear_visits`) lets the user clear what they see — it does **not** delete or modify any `Visit` row; it upserts a `HistoryClear(user_id, cleared_at)` marker (a dedicated table, not a column on `User`/`Visit`, precisely so `create_all`'s no-`ALTER` behavior didn't force a `sinchon_guide.db` reset — see `models.py` and the Commands section above), and `list_visits` filters out rows at/before that cutoff. Deliberately, the personalization query in `routers/recommendations.py` (`visit_counts_by_place`) never consults `HistoryClear` — it reads `Visit` directly, so a cleared visit keeps counting toward recommendations forever; clearing is a visible-history concept only. Repeat clears just push the cutoff forward, so a visit made after a clear naturally reappears until the next one.

### Frontend

- **No navigation library.** `App.tsx` holds a manual `route` state (`'ask' | 'guide' | 'history'`), but **`AskScreen` is always mounted** — `GuideScreen` and `HistoryScreen` are layered on top of it via `CrossfadeSwitch` (`visible={route === 'guide'}` / `'history'`), not swapped in via a route-keyed conditional render. This is deliberate: an earlier version rendered `{route === 'guide' ? <GuideScreen/> : <AskScreen/>}` directly, which unmounted `AskScreen` on every trip to `GuideScreen` and reset it to its initial `'type'` step on return — so pressing "다시 추천받기" looked like it dumped the user back to the home screen instead of the result they'd picked from. `backToAsk()` also deliberately does **not** clear `picked`/`need` — it only flips `route`, leaving `GuideScreen` mounted-but-hidden so its own state (fetched route, map) survives the round trip too; `HistoryScreen` follows the same pattern via a one-way `hasOpenedHistory` flag (set on first open, never cleared) so its own crossfade-out has something to animate instead of unmounting mid-fade. Auth gating happens in `Root` via `src/auth/AuthContext.tsx` (token persisted with AsyncStorage in `src/api/authStore.ts`); no token → `AuthScreen` directly.
- `AuthScreen` — 로그인 needs only 이메일/비밀번호; 회원가입 additionally asks 이름/생년월일/닉네임. The 생년월일 field auto-formats digits into `YYYY-MM-DD` as the user types (`formatBirthDate` strips non-digits and re-inserts the hyphens) so the user never has to type `-` themselves; `DATE_RE` validation expects exactly that shape.
- `AskScreen` — a 2-step button flow: `type → result` (≤4 options). Picking a need type calls `/recommendations` immediately and caches the full ranked candidate list. The result step shows the top candidate as a hero — name, `RatingStars` (or "평점 없음"), an `OpenStatusBadge`, and a `PlaceMeta` line (walk time + category) — plus every other candidate below it as a scrollable "다른 후보" comparison list, each one tappable straight into `onGuide`; this replaced an earlier one-at-a-time, forward-only "다른 곳 추천받기" reroll that could never step back to a previously shown place once the user moved past it. The error state adds a "다시 시도" action that re-runs the same query (previously the only recovery was "처음부터", a full restart); the empty state's copy now nudges toward trying another category. A header ☰ button (`onOpenHistory`) opens `HistoryScreen`. **No budget step**, and this has happened twice for two different reasons: first because Kakao (the search provider) has no price data at all; then, after `services/enrichment.py` started fetching Google's `priceLevel` and the budget step was briefly restored, it was dropped *again* because live testing across `가성비`/`적당히`/`플렉스` at the same Sinchon coordinates showed only 1 of 12 candidates ever got a non-null `price_level` back from Google, and even that one candidate's budget-fit tiebreaker (weight capped at 2 points) was too small next to distance (`distance_minutes × 10`) and rating (up to 5.0) to matter — the three budgets produced near-identical or fully identical results. So this time the fix isn't "wait for a data source" — a data source exists — it's "the data's too sparse and the tiebreaker's too weak for the question to be worth asking." `Need.budget` stays in the wire contract with a constant `'mid'` value (still recorded on `Visit`, trivially revivable if this ever changes) — only the UI question and the scoring use are gone; see `services/recommendation.py` and `services/enrichment.py` above. Produces `Need = {type, budget, lat, lng}` (`src/types/recommendation.ts`) — this is the categorization contract. A future free-text/LLM input stage just needs to emit this same shape; nothing downstream changes.
- `GuideScreen` — fetches the walking route for the picked place, renders `LiveMapView` with the pick marker, the route as a `NaverMapPathOverlay` (coordinates come straight from `POST /routes`, no decoding needed), and the live user-location dot. The bottom card shows `RatingStars` (or "평점 없음"), an `OpenStatusBadge`, and a `PlaceMeta` line (walk time, category, address), plus a "네이버 지도로 안내" button that opens Naver Map's walking-directions deep link (`nmap://route/walk?...`, falling back to the Play Store listing if not installed) — it no longer writes the `Visit` itself; see `routers/visits.py` above for why that moved to `App.tsx`'s `openGuide`.
- `HistoryScreen` — opened from `AskScreen`'s header ☰ button. Shows the logged-in user's nickname/email plus a **로그아웃** button (wired to `AuthContext.logout`, which existed with no UI surface until this screen), and the visit history from `GET /visits`. Takes a `visible` prop and refetches every time it transitions into view rather than only on first mount, since `App.tsx` keeps it mounted-but-hidden like `GuideScreen` — otherwise a visit recorded after the screen's first open would only ever show up after a fresh app relaunch. A "기록 지우기" action (behind an `Alert.alert` confirmation whose copy states exactly what happens) calls `DELETE /visits`; see `routers/visits.py` above for why this never touches the recommendation scorer's personalization signal.
- `src/hooks/useUserLocation.ts` + `src/services/locationService.ts` — the location source for both screens' `Need.lat/lng` and map regions. Falls back to a fixed Sinchon-station coordinate when permission is denied/unavailable (never some other neighborhood, since that would silently mis-locate every downstream Places search); `regionCovering()` computes the smallest region framing two coordinates (user + destination) without needing a `MapView` ref. Also runs a continuous `watchPosition` once the initial fix is granted, since (unlike `react-native-maps`) Naver's location overlay has no GPS tracking of its own — the app must keep feeding it a fresh coordinate for the live dot to actually move. **`USE_MOCK_LOCATION` (`locationService.ts`, on by default under `__DEV__`) overrides both `requestCurrentLocation()` and `watchPosition()` to a fixed Yonsei-main-gate coordinate.** This exists because the Android emulator's default GPS fix is Google HQ in Mountain View, California — a *granted* permission, so the denied/unavailable fallback above never kicks in — which silently sent the whole app (recommendations, routes, map) to the wrong continent (nonsensical `도보 N분` distances, `/routes` failing since TMAP can't route California→Seoul). Flip the flag off to test against a real/emulator-set GPS fix.
- `src/design/` — the shared style/token layer (`theme.ts` colors/spacing/radius/typography/shadow; `shellStyles.ts` panel/prompt-card shells, incl. the `chip`/`chipText` pill reused by `OpenStatusBadge`; `layout.ts` screen scaffolding). `src/components/` holds the presentational/animation primitives built on it (`AppButton`, `IconButton`, `TouchableFade`, `MapMarkerPin`, `BottomActionBar`, `PhaseIndicator`, `AnimatedHint`, `ScreenTransition`, `CardTransition`, `CrossfadeSwitch`, `RatingStars`, `OpenStatusBadge`, `PlaceMeta`) — screens compose these rather than styling inline. `RatingStars` renders an explicit "평점 없음" (never blank) when `rating` is null — Google only enriches the nearest few candidates (see `services/enrichment.py`), so a missing rating is a common, expected state, not an error — plus a `(N)` rating-count suffix when Google supplied `userRatingCount`. `OpenStatusBadge` renders 영업 중/영업 종료/영업정보 없음 from `openNow`; `null` renders as "영업정보 없음" rather than nothing, since hiding it entirely is exactly how a user could get routed to a closed place with no warning. `PlaceMeta` renders the walk-time + category line (plus address, only on `GuideScreen`'s card).
- `src/constants/needTypes.ts` — the single source of the Korean label per need type (식사/카페/술 한잔/디저트), shared by `AskScreen`'s picker buttons and `HistoryScreen`'s history rows so the two can't silently drift out of sync on wording.
- `src/api/config.ts` picks the API host per platform: Android emulator → `10.0.2.2:8000`, iOS simulator → `localhost:8000`. Physical devices need the machine's LAN IP edited in that file.
- **Current focus: Android only. iOS is deferred** (see *iOS status* below). Android is developed and tested on an Android Studio emulator with a Google Play Services system image (native build via `npm run android`; see *Maps and place search* below for why that system image is still recommended even though Google is no longer the map/place provider) — this is the only supported dev/demo target right now.

### Maps and place search — off Google for map/search/routing, back for enrichment only

Map rendering moved to Naver, routing moved to TMAP, and place *search breadth* moved to Kakao —
Google plays no role in any of those three stages, and per *Routing in South Korea* / the
*Place search: Kakao Local API* section below, none of them are coming back to Google. Google
**did** come back, in a fourth, narrower role added later: `services/enrichment.py` calls
**Google Places API (New)**'s Text Search per Kakao candidate to fill in `rating`/`open_now`,
which none of Kakao/Naver/TMAP expose (`priceLevel` was fetched here too at first but was
dropped — see `services/enrichment.py`'s Architecture bullet above). This is enrichment of
Kakao's results, not a replacement for Kakao search — see `services/enrichment.py`'s
Architecture bullet above for how matching/fail-soft degradation works, and the env-var section
above for the key's required (non-)restriction settings.

**What each API actually does — each owns exactly one stage, no overlap:**

- **Kakao Local API** (backend, `KAKAO_REST_API_KEY`) — finds *what's nearby*. Given the user's
  location + need type, returns real businesses (name, coordinates, category) within ~1.2km.
  This is the candidate data `services/recommendation.py` ranks. Called from `services/places.py`.
- **Google Places API (New)** (backend, `GOOGLE_PLACES_API_KEY`) — fills in *what Kakao can't
  say*: rating and open-now, for the nearest few candidates only. Called from
  `services/enrichment.py`, after Kakao search and before scoring. (Also tried price level —
  dropped; see `services/enrichment.py`'s Architecture bullet.)
- **TMAP Pedestrian Route API** (backend, `TMAP_APP_KEY`) — computes *how to walk there*. Given
  a start/end coordinate pair (only for the place the user actually picked), returns the walking
  path geometry + distance/time. Called from `routers/routes.py`.
- **Naver Maps SDK** (frontend, `naver_map_client_id`) — *draws it all on screen*: the map tiles,
  the live user-location dot, the destination pin, and the TMAP-supplied route line. Purely
  client-side rendering — it doesn't search for places or compute routes itself.

- `src/components/LiveMapView.tsx` wraps `@mj-studio/react-native-naver-map` (`NaverMapView`), replacing `react-native-maps`/Google as the map renderer — Android only for now (see *iOS status*); the JS is platform-agnostic so iOS just needs its native Naver setup added later. `MapMarkerPin` wraps `NaverMapMarkerOverlay`; `GuideScreen`'s route line is a `NaverMapPathOverlay`. **`MapMarkerPin` requires explicit `width`/`height` props** (matching its child `View`'s own size, e.g. `GuideScreen`'s `PIN_SIZE` constant) — a custom-`View` marker (as opposed to an image marker) has no intrinsic size for the native side to measure, and `NaverMapMarkerOverlay` silently renders nothing at all for it without an explicit size, rather than falling back to a default. This bit us once already (destination pin missing while the route line rendered fine) — if a pin silently stops appearing after touching `MapMarkerPin`, check this first.
- No OpenStreetMap/tile-overlay dependency.
- **Four fully independent keys/credentials, four unrelated providers** — don't conflate them:
  - `frontend/.env` (gitignored): `naver_map_client_id` — Naver Cloud Platform (NCP) Maps client ID, renders the native map view only. **One client ID covers both platforms** (the NCP application is registered with both an Android package name and an iOS bundle ID) — no `_android`/`_ios` suffix needed. `android/app/build.gradle` reads it and injects it into `AndroidManifest.xml` via a `manifestPlaceholder` (`com.naver.maps.map.NCP_KEY_ID`); iOS wiring (Info.plist) is added when iOS work resumes. Requires the Naver Maven repo (`https://repository.map.naver.com/archive/maven`) added to `android/build.gradle`.
  - Backend env: `TMAP_APP_KEY` (SK Open API — TMAP Pedestrian Route API, the walking-path data for `routers/routes.py`). Server-side only, read lazily via `services/api_errors.require_tmap_key()`. The app registered for this key must have the **보행자 경로안내 (Pedestrian)** product subscribed — a **TMAP 대중교통 (Transit)**-only key will not authorize this endpoint.
  - Backend env: `KAKAO_REST_API_KEY` (Kakao Developers — Local API, the place-search data for `services/places.py`). Server-side only, read lazily via `services/api_errors.require_kakao_key()`. Use the app's **REST API key**, not its JavaScript or Native App key — those are for client-side/native SDK auth, not server calls.
  - Backend env: `GOOGLE_PLACES_API_KEY` (Google Cloud — Places API (New), the rating/open-now enrichment data for `services/enrichment.py`). Server-side only, read lazily via `services/api_errors.require_google_key()`. Must have **Places API (New)** enabled. Must **not** be IP-restricted while the backend runs on a dynamic dev-machine IP (see the env-var section above and *Place search* below for why this specific mistake already happened once).
- The Android emulator's AVD historically needed a **Google Play Services** system image for the Google Maps SDK to render; that specific reason is gone now that rendering is Naver, but Play Services still benefits `@react-native-community/geolocation`'s location accuracy, so keep using a Play-Services image unless you have a specific reason not to.
- `Linking.canOpenURL('nmap://...')` (used by `GuideScreen`'s handoff button) requires a `<queries>` entry for the `nmap` scheme in `AndroidManifest.xml` — Android 11+ package-visibility rules make it silently return `false` otherwise, even with Naver Map installed.

### Place search: Kakao Local API (Google Places search removed; enrichment added back later)

Google Places was the last remaining Google dependency (map rendering and routing had already
moved to Naver/TMAP) and kept causing the exact failure `googleghost.png` shows: a 403 because
`GOOGLE_MAPS_SERVER_KEY` was IP-restricted and the dev machine's IP had changed.

Naver was investigated as a replacement and ruled out: NCP's Maps product family (the same
console `naver_map_client_id` comes from) has exactly five products — Dynamic Map, Static Map,
Directions 5/15, Geocoding, Reverse Geocoding — no place/POI search API at all. Naver's Local
Search API (`openapi.naver.com`, a *different* Naver platform than NCP) is keyword-only text
search, capped at 5 results, with no coordinate/radius parameter — a poor fit for
"closest-first, radius-bounded" search. No official Naver API exposes menu/price data either
(the menu/price shown in the consumer Naver Map app is SmartPlace business-listing data with no
public REST endpoint).

**Fix applied:** `services/places.py` now calls **Kakao's Local API** — `category.json` for
`meal`/`cafe` (clean `category_group_code` buckets), `keyword.json` for `drinks`/`dessert`
(Kakao has no dedicated category code for bars/dessert shops — see the bullet above). Same
1.2km radius, same defensive category post-filter pattern as the Google-era code. **Neither
Kakao nor Naver expose rating/price-level/open-now** — this held true until Google was later
brought back in an enrichment-only role for rating/open-now (see below); price-level was tried
too but dropped again — see the third paragraph.

**Google Places re-added, narrower role (later change):** since neither Kakao nor Naver ever
gained a rating/open-now API, `services/enrichment.py` now calls **Google Places API (New)**'s
Text Search — but only per-candidate, only for the nearest few candidates, and only to fill in
those two fields; Kakao stays the sole source of search breadth/candidates. This is not a
reversal of the fix above (Kakao search removal), and it doesn't reintroduce the
`googleghost.png` failure mode as long as the new `GOOGLE_PLACES_API_KEY` is kept
**non**-IP-restricted on a dynamic dev IP (see the env-var section and *Maps and place search*
above). See `services/recommendation.py`'s Architecture bullet for how the scorer uses this data.

**Price-level tried and dropped (later still):** this enrichment pass originally also fetched
`priceLevel`, feeding a `budget_fit` tiebreaker in `services/recommendation.py` and a restored
budget question in `AskScreen`. Live A/B testing at Sinchon station across `가성비`/`적당히`/
`플렉스` showed the idea didn't pay off: only 1 of 12 candidates ever got a non-null
`price_level` from Google, and the tiebreaker's weight (capped at 2 points, by design a
near-tie-breaker) was too small next to distance/rating to matter even then — the three budgets
produced near-identical or fully identical recommendations. `price_level` fetching, the
`budget_fit` scoring term, and the `AskScreen` budget step were all removed as a result; see the
`AskScreen` bullet above for the full reasoning and `services/enrichment.py`'s Architecture
bullet for what's still fetched.

### Routing in South Korea: Google Routes doesn't work, TMAP does

Google Routes' `computeRoutes` reliably 404s ("No walking route found") for every real Sinchon origin/destination pair — confirmed by calling it directly with Sinchon coordinates (HTTP 200, empty `{}` body, no `routes` key) versus the identical request shape with non-Korea coordinates (returns a normal route). This isn't a key, field-mask, or request-format problem: South Korea's Act on National Spatial Data Infrastructure restricts export of detailed (1:5,000-scale) map data to servers outside the country, and Google's routing servers are outside Korea. Google can still return place *search* results (Places API is unaffected) but not turn-by-turn route geometry. Conditional export approval was granted in Feb 2026, but as of this writing it has not produced working API routing.

**Fix applied:** `routers/routes.py` now calls **TMAP's Pedestrian Route API** (`apis.openapi.sk.com/tmap/routes/pedestrian`) instead — TMAP is a Korea-based provider and isn't subject to the export restriction. The response (GeoJSON `LineString`/`Point` features) is transformed by the pure `tmap_geojson_to_route()` into `RouteOut.coordinates`, a plain `{latitude, longitude}` list that feeds `NaverMapPathOverlay` directly (no polyline encode/decode round trip — that machinery was removed along with `react-native-maps`). The in-app map render also moved to Naver Map for the same underlying reason (see *Maps* above), and `GuideScreen`'s external handoff button now opens Naver Map's walking-directions deep link instead of Google Maps.

### iOS status (deferred)

Out of scope right now — captured here so the constraints aren't rediscovered later. Despite the branch being named `expo`, **no Expo tooling is installed** (this is bare React Native CLI). The Windows dev machine has **no iOS Simulator** (requires macOS/Xcode), so iOS needs a physical device or a Mac. Two possible paths, each with trade-offs:

- **Stock Expo Go on a physical iPhone** — a fixed prebuilt binary that runs the JS bundle but **cannot load custom native pods**. Only modules Expo Go already ships work: `react-native-safe-area-context` ✅, `@react-native-async-storage/async-storage` ✅ — but **`@react-native-community/geolocation` ✗** (Expo ships `expo-location` instead) and **`@mj-studio/react-native-naver-map` ✗** (not an Expo Go built-in; it does ship an Expo config-plugin for prebuild, but that only helps the *next* path, not stock Expo Go). So on this path the map wouldn't render at all, not just fall back to Apple Maps — this path is effectively closed now that the renderer is Naver, not `react-native-maps`.
- **Custom dev client via EAS Build** — cloud macOS build, no local Mac required; supports all native modules (geolocation, Naver Map's iOS SDK via its Expo config-plugin or manual Podfile wiring) but needs EAS setup and a physical device. This is now the only realistic iOS path.

The backend's web-service APIs (Kakao Local, TMAP Routes) are plain HTTPS `fetch` calls from the **backend**, not native modules on the client — so they work regardless of which iOS path is chosen, once iOS is picked back up.

### Android native build (Windows)

- New Architecture is on (`newArchEnabled=true` in `android/gradle.properties`), so every native module gets a Fabric codegen C++ target compiled via CMake/Ninja. **Do not set this to `false`** — RN 0.85's app-level build runs the Fabric/CMake configure step unconditionally regardless of this flag, but a third-party library's own `build.gradle` (e.g. `@mj-studio/react-native-naver-map`'s) typically gates *its own* codegen generation behind this same property. Flip it to `false` and the app still tries to `add_subdirectory` into that library's (now never-generated) `.../android/build/generated/source/codegen/jni/`, which fails CMake configure with "which is not an existing directory" — this is exactly what happened on this branch (commit `abb258e`, "I can't deal with the guidance issue", turned it off as a workaround attempt and never turned it back on) and cost real time to root-cause. If you hit that CMake error after adding a native dependency, check this flag first. CMake also mirrors each source file's full absolute path under the build directory, which on Windows can blow past the 260-character `MAX_PATH` limit — this repo's own path (`...\Private Files\Programming\sinchon_guide\frontend\node_modules\...`) is long enough to trigger it (hit first on `react-native-safe-area-context`).
- `android/app/build.gradle` sets `externalNativeBuild.cmake.buildStagingDirectory` to a short temp-dir path to shave the build-dir prefix, but that alone isn't sufficient — the mirrored `node_modules` source path is the bigger contributor. The real fix is enabling Windows long-path support (`LongPathsEnabled=1` registry key + `git config --system core.longpaths true`, needs a reboot) or moving the project to a short path. If a `Filename longer than 260 characters` Ninja error resurfaces after adding a new native dependency, this is why.
- Gradle's autolinking (`settings.gradle`'s `autolinkLibrariesFromCommand()`) caches its `react-native config` output in `android/build/generated/autolinking/` and `android/app/build/generated/autolinking/`, gated by a hash of `package.json`/`package-lock.json` — it only re-runs when that hash changes. If a native package is added to `package.json` *before* it's actually present in `node_modules` (e.g. committed mid-install, or `npm install` interrupted), the hash is already "current" by the time `node_modules` catches up, so a later `npm install` alone won't invalidate the cache — the module silently never gets linked (missing from the generated `PackageList.java`, no Fabric view manager compiled), even though `npx react-native config` correctly reports it and the app builds/installs without error. Symptom: a JS-level "Cannot read property '<Component>' of undefined" for a native view, only when that screen actually mounts — a plain Metro cache reset + `npm run android` rebuild does *not* fix this, since the stale autolinking cache is untouched by either. Fix: delete `android/build/generated/autolinking/` and `android/app/build/generated/autolinking/` (or `./gradlew clean`) to force regeneration, then rebuild. Hit with `@mj-studio/react-native-naver-map` on this branch after it was reinstalled following an earlier missing-`node_modules` incident.
